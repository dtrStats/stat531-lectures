Where we left off

Verbs from Session 1, all working on rows and columns:

select picks columns · filter picks rows

arrange sorts · mutate adds columns

slice_* picks rows by position · count tallies

Every one of them returns a table with the same or fewer rows. None of them can collapse a table into a summary.

Questions the verbs cannot answer

Which genre do audiences like best?

Which studio’s films score highest?

How many views per device in a log with 4 million rows?

Each one needs a new move: group, combine, or scale.

Auditing an AI summary

Before you trust a grouped result, ask:

  1. What is a row? One film, one genre, one person?
  2. Grouped by what? Right level, no hidden groups left?
  3. What happened to NA? Dropped, kept, or ignored?
  4. How big is each group? Is n shown?

A left_join should return exactly as many rows as the left table (when the key is unique on the right).

Find the duplicate key

studios_v2 |> count(studio) |> filter(n > 1)
#> # A tibble: 1 x 2
#>   studio                 n
#>   <chr>              <int>
#> 1 Paramount Pictures     2

Make R refuse bad joins

movies |>
  left_join(studios_v2, by = "studio", relationship = "many-to-one") |>
  nrow()
#> Error in `left_join()`:
#> ! Each row in `x` must match at most 1 row in `y`.
#> i Row 18 of `x` matches multiple rows in `y`.

relationship = "many-to-one" says: each movie matches at most one studio row. Break that, and R stops.

Join checklist

Before and after every join:

  1. Keys unique on the lookup side? count(key) |> filter(n > 1)
  2. Row count as expected?
  3. New NAs? anti_join shows which keys failed.
  4. Right join type: left keeps, inner drops.

When the file is bigger than your memory

A simulated log of 4 million viewing events:

Format Size on disk
CSV 239 MB
Parquet 40 MB

read_csv() would pull all 4 million rows into R’s memory (about 229 MB here). A real log could be 400 million.

What is Parquet?

  • Columnar: stores each column together, so R reads only the columns you ask for
  • Typed: dates stay dates, numbers stay numbers
  • Compressed: much smaller than CSV
  • Self-describing: the schema lives inside the file

Setup

install.packages("arrow")   # once
library(arrow)
library(tidyverse)

Today’s file: data/views.parquet. Columns: view_id, title, user_id, country, device, view_date, minutes, completed.

views <- open_dataset("data/views.parquet")

Interaction 3: where does collect go?

# Pipeline A
views |> collect() |> filter(country == "US") |> count(device)

# Pipeline B
views |> filter(country == "US") |> count(device) |> collect()

Turn to your neighbor (3 min): same answer? Which one would you let an AI run on 400 million rows?

INTERACTION 3 of 3. Give 3 minutes. Answer: both give the same answer. Pipeline A loads ALL rows into memory first (about 229 MB here, tens of GB on a real log), then filters. Pipeline B filters and counts inside arrow and brings back 4 rows. Rule: shrink first, collect last.

The answer

Same result. Very different cost.

A loads every row, then filters. B filters first, then collects 4 rows.

. . .

Bug to look for: an early collect(), as.data.frame(), or as_tibble(). It silently pulls the whole dataset into memory.

Not every R function runs in arrow

arrow translates many dplyr verbs and functions. A few things it cannot run.

When you see an error that mentions an unsupported function:

  1. collect() only after shrinking the data
  2. Then use the full R function on the small result

Never fix it by moving collect() to the top.

Big-data checklist for AI code

  1. Filter and select first: fewer rows, fewer columns
  2. collect() last: after the data is small
  3. Check the shape: how many rows came back?
  4. Check the memory: Environment pane, or object.size()

Appendix

Other joins

movies |> full_join(studios, by = "studio") |> nrow()
#> [1] 651
movies |> semi_join(studios, by = "studio") |> nrow()
#> [1] 402
  • full_join: keep all rows from both tables (651 films + lookup rows never used)
  • semi_join: keep left rows that have a match (like inner_join, but adds no columns)

Many-to-many joins

If a key repeats on both sides, every pair matches. Rows multiply.

dplyr warns: “Detected an unexpected many-to-many relationship.”

left_join(movies, studios_v2, by = "studio", relationship = "many-to-many")

Only silence the warning when many-to-many is exactly what you intend.

Writing and reading Parquet

write_parquet(movies, "data/movies.parquet")
movies_pq <- read_parquet("data/movies.parquet")   # reads fully into memory

open_dataset() is lazy. read_parquet() loads everything. For a folder of many Parquet files, point open_dataset() at the folder.
